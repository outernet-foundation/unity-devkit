# plan-single-workflow-pin.md — one SHA pin per consumer repo for the build workflow

This is an execution plan. A session with no prior context should be able to execute it top to bottom. No review gate — the owner has approved this architecture.

## 1. Why this exists

Each consumer repo that does player builds pins `outernet-foundation/unity-devkit/.github/workflows/build-unity.yml@<SHA>` in **two** workflow files:

1. `build-dispatch.yml` — generated by `unity-dispatch`, a `workflow_dispatch` workflow with one input per environment field. The SHA comes from the `--build-workflow` argument passed to the generator.
2. `ci.yml` — hand-written, push-triggered CI. The SHA is typed manually.

These two SHAs are maintained independently (one generated, one hand-typed) and nothing keeps them in sync. This caused a live CI failure on 2026-09-28: the generator bumped `build-dispatch.yml` to `cd7ac90` but `ci.yml` was still at `b61dc729`, so CI ran the old workflow (old `upload-artifact` code, quota block).

The OCI migration (plan-oci-migration.md, complete) eliminated the *package-version* pin — with the uvx conversion, the workflow SHA now pins both the workflow YAML and the Python package version (`UNITY_DEVKIT_VERSION` env var in the workflow). One pin instead of two. But the *dual-SHA-within-consumer-repos* problem remains: the same SHA is referenced in two files per repo, and they drift.

## 2. Current state

### Hosted workflows in unity-devkit

- **`build-unity.yml`** — a `workflow_call` reusable workflow (the "engine"). Inputs: `runner-labels`, `environment-preset`, `development`, `environment-fields`, `version`. Internally calls `prepare-unity.yml` (matrix generation + license activation), then runs `ci-build-unity` via `uvx`. Consumers pin it by SHA.
- **`compile-check-unity.yml`** — a `workflow_call` reusable workflow for compile-only gates. Out of scope for this plan (consumers that use it reference it once — no drift problem).
- **`prepare-unity.yml`** — internal, called by the above. Not consumer-facing.

### Generated file in consumer repos

- **`build-dispatch.yml`** — generated by `unity-dispatch` (a unity-devkit Python entry point). The generator runs the playerbuild dump door (`Outernet.PlayerBuild.DumpEnvironment`) in Unity batchmode, reads the consumer's environment class fields, and renders a `workflow_dispatch` YAML with one input per field (dropdowns for enums, checkboxes for booleans). The `--build-workflow ...@<SHA>` argument is baked into both the header comment and the `uses:` line. The file is committed to the consumer repo.

### Hand-written file in consumer repos

- **`ci.yml`** — push-triggered CI. Has a `unity` job that calls `build-unity.yml@<SHA>` directly with just `runner-labels` (and optionally `version`). Not generated — the SHA is hand-typed.

### Consumer repos affected

- **`Make-it-Sing-fork`** (private, `dev` branch) — has `MakeItSing-Unity/unity-devkit.json` with platforms. `ci.yml` unity job passes `runner-labels` only.
- **`placeframe-capture-tool`** (public, `main` branch) — has `apps/CaptureTool/unity-devkit.json` with platforms. `ci.yml` unity job passes `runner-labels` + `version` (from a `resolve-version` job).

### The `unity-dispatch` generator

Entry point: `dispatch_workflow_generator.py` in `packages/python/unity-devkit/src/unity_devkit/`. The `--build-workflow` argument is the full cross-repo reference (`owner/repo/.github/workflows/build-unity.yml@<SHA>`). The generator bakes it into the emitted `uses:` line, the regen header comment, and the drift message. `--check` regenerates and diffs (exists but is not wired into consumer CI — and this plan deliberately does not add it).

Test: `packages/python/unity-devkit/tests/test_dispatch_workflow_generator.py` — verifies the generated output structure. Will need updating when the generator's output template changes.

## 3. The migration

### Rename the hosted engine

Rename `build-unity.yml` → `build-unity-internal.yml` in unity-devkit. Same workflow, same `workflow_call` surface, same inputs. The name signals "this is the engine, not what consumers interact with." The generator's `--build-workflow` argument will reference `build-unity-internal.yml@<SHA>` instead of `build-unity.yml@<SHA>`.

### Rename the generated consumer file

Rename `build-dispatch.yml` → `build-unity.yml` in consumer repos. Kept directly in `.github/workflows/` (NOT a subdirectory — GitHub Actions only discovers workflows in the top level of `.github/workflows/`, not subdirectories; a file in `.github/workflows/generated/` would not be triggerable via `workflow_dispatch`). This file becomes the single entry point for both manual dispatch and CI.

### Add `workflow_call` to the generated file

The generated `build-unity.yml` gets a second trigger alongside `workflow_dispatch`:

```yaml
on:
  workflow_dispatch:
    inputs:
      environment-preset: ...
      development: ...
      ...                           # all the existing dispatch inputs, unchanged
  workflow_call:                    # NEW — minimal inputs for CI callers
    inputs:
      runner-labels:
        description: JSON-encoded runs-on value
        type: string
        default: '"ubuntu-latest"'
      version:
        description: Version string to stamp; empty builds unversioned
        type: string
        default: ''
```

The build job's `with:` block uses `||` defaults so each trigger sees only its own inputs:

```yaml
jobs:
  build:
    uses: outernet-foundation/unity-devkit/.github/workflows/build-unity-internal.yml@<SHA>
    with:
      runner-labels: ${{ inputs.runner-labels || '"ubuntu-latest"' }}
      version: ${{ inputs.version || '' }}
      environment-preset: ${{ inputs.environment-preset || '' }}
      development: ${{ inputs.development || false }}
      environment-fields: |-
        ${{ inputs['runInOfflineMode'] && format('runInOfflineMode={0}', inputs['runInOfflineMode']) || '' }}
        ...
    secrets: inherit
```

When `workflow_dispatch` triggers the workflow, the `workflow_call` inputs (`runner-labels`, `version`) are undefined — the `||` defaults kick in. When `workflow_call` triggers it, the `workflow_dispatch` inputs (`environment-preset`, `development`, the environment fields) are undefined — they fall back to empty/false. Each trigger sees only its own inputs; the `||` defaults handle the other case. This is standard GitHub Actions behavior — `inputs` from a non-triggering event are simply absent.

### Change consumer `ci.yml`

The `unity` job calls the local generated file instead of the external hosted workflow:

**Make-it-Sing-fork `ci.yml` (before):**
```yaml
  unity:
    needs: [check]
    permissions:
      contents: read
      packages: write
    uses: outernet-foundation/unity-devkit/.github/workflows/build-unity.yml@ec46fb5...
    with:
      runner-labels: '["self-hosted","unity"]'
    secrets: inherit
```

**Make-it-Sing-fork `ci.yml` (after):**
```yaml
  unity:
    needs: [check]
    permissions:
      contents: read
      packages: write
    uses: ./.github/workflows/build-unity.yml
    with:
      runner-labels: '["self-hosted","unity"]'
    secrets: inherit
```

**placeframe-capture-tool `ci.yml` (after):**
```yaml
  unity:
    needs: [check, resolve-version]
    permissions:
      contents: read
      packages: write
    uses: ./.github/workflows/build-unity.yml
    with:
      runner-labels: '["self-hosted","unity"]'
      version: ${{ needs.resolve-version.outputs.version }}
    secrets: inherit
```

No SHA in `ci.yml` — it calls a local file. The SHA lives only in the generated `build-unity.yml`.

### Generator change

`dispatch_workflow_generator.py` changes:
1. Emit `workflow_call` trigger alongside `workflow_dispatch` in the output template
2. Add `runner-labels` and `version` to the `workflow_call` inputs
3. Add `runner-labels: ${{ inputs.runner-labels || '"ubuntu-latest"' }}` and `version: ${{ inputs.version || '' }}` to the build job's `with:` block (before the existing environment-preset/development/environment-fields entries)
4. The `--build-workflow` argument is passed through unchanged — the user passes `.../build-unity-internal.yml@<SHA>` instead of `.../build-unity.yml@<SHA>`
5. The `--output` argument is passed through unchanged — the user passes `.github/workflows/build-unity.yml` instead of `.github/workflows/build-dispatch.yml`

The header comment updates automatically (it echoes the `--output` and `--build-workflow` arguments).

### No staleness gate

The generated file has a header comment ("Generated by 'uv run unity-dispatch ...'") indicating it is generated. No CI staleness check. The `--check` flag exists on `unity-dispatch` for manual verification but is deliberately not wired into consumer CI — the cost (needs a Unity container + license to re-run the dump door) outweighs the benefit for this specific artifact.

## 4. Result

One SHA per consumer repo, in the generated `build-unity.yml`'s `uses:` line. A SHA bump = re-run the generator:

```
uvx --from unity-devkit unity-dispatch \
  --project MakeItSing-Unity \
  --output .github/workflows/build-unity.yml \
  --build-workflow outernet-foundation/unity-devkit/.github/workflows/build-unity-internal.yml@<new-SHA>
```

`ci.yml` picks it up automatically because it calls `./.github/workflows/build-unity.yml` (local file, no SHA). Drift is impossible — there's nothing to drift against.

## 5. Execution order

Steps 1–3 are in unity-devkit (code + prose). Steps 4–5 are in each consumer repo. Steps 1–3 must land and be pushed before steps 4–5 (consumers need the new generator and the renamed engine).

1. **Rename `build-unity.yml` → `build-unity-internal.yml`** in unity-devkit. Update any internal references (`ci.yml` doesn't call it, but check). Commit (code).

2. **Update `dispatch_workflow_generator.py`** to emit `workflow_call` alongside `workflow_dispatch`, with `runner-labels`/`version` call inputs and `||` defaults in the build job's `with:` block. Update `test_dispatch_workflow_generator.py` expectations. Run ruff + basedpyright + pytest. Commit (code).

3. **Update unity-devkit AGENTS.md** — the `unity-dispatch` entry and the "Entry-point names are the workflow contract" section reference `build-unity.yml` (the hosted engine); update to `build-unity-internal.yml`. Commit (prose, separate from code).

4. **In each consumer repo** (Make-it-Sing-fork on `dev`, placeframe-capture-tool on `main`):
   - Delete `build-dispatch.yml` (`git rm`)
   - Re-run the generator to produce `build-unity.yml` at `.github/workflows/build-unity.yml` with `--build-workflow .../build-unity-internal.yml@<new-SHA>` (the SHA of the unity-devkit commit from step 2 or 3, after it's pushed)
   - Update `ci.yml`'s `unity` job: `uses: ./.github/workflows/build-unity.yml` (local, no SHA), keep the `with:` inputs (`runner-labels`, and `version` for placeframe-capture-tool)
   - Commit (code — all YAML, no prose)

5. **Operator pushes** all three repos. The App token is `Contents: read` only — pushes are the operator's job.
